# v0.34 Opponent Stat Sample Assumption Design

Status: design only  
Date: 2026-05-27

## 1. Current State

The app already has user-entered final stat support, but it does not have an opponent sample stat layer.

Current relevant behavior:

- `StatProfileDialog` lets T1 enter final stats for either active Pokemon through the existing Stats button.
- `PokemonPanel.final_stats` stores those entered values.
- `MainWindow._stat_profile_payload()` emits either:
  - `status: "user_confirmed_final_stats"` with `source: "user_input"` when all six final stats are present, or
  - `status: "default_assumption"` with `source: "system_default"` when final stats are absent or incomplete.
- `llm/advisor_damage_estimate.py` uses user-confirmed final stats when present.
- Damage estimates otherwise fall back to default Level 50, IV 31, EV 0, neutral-nature stats.
- `speed_context` is created only when both active Pokemon have user-confirmed final Speed.
- `speed_context` may include Choice Scarf effective Speed only from a user-confirmed item.
- `speed_context.is_final_turn_order` remains `false`.
- The payload contract and tests already distinguish default assumptions from user-confirmed final stats.
- There is no `sample_assumed` stat source, no sample stat fixture, no sample repository, and no sample selector UI.

Important current limitation:

- The opponent's actual final stats are usually unknown unless T1 directly confirms them.
- The current default assumptions are useful rough references, but they are the lowest-confidence stat model.

## 2. Problem Definition

Opponent final stats are tactically important, but usually not directly visible.

T1 may eventually maintain manually curated or meta-informed sample stat profiles, such as:

- fast physical Garchomp
- bulky Corviknight
- offensive Charizard

Those samples are useful assumptions, but they are not the same as user-confirmed opponent stats. If the app sends sample stats in the same shape as `user_confirmed_final_stats`, the LLM may overclaim:

- exact opponent Speed
- exact damage
- guaranteed outspeed
- KO/OHKO/2HKO or survival outcomes
- final turn order

The design must keep three ideas separate:

- stats T1 directly confirmed
- stats assumed from a named sample
- stats generated by the app's default fallback

Damage estimates, speed comparisons, and future survival/KO reasoning should all surface stat source and confidence. Sample stats may improve the usefulness of rough references, but they must never be described as the opponent's actual spread.

## 3. Stat Source Model

### A. `user_confirmed_final_stats`

Meaning:

- T1 directly entered all six final stats.
- This is the highest-confidence currently available stat source.
- It may be used by damage estimates and raw/effective Speed comparison.

Payload semantics:

```json
{
  "status": "user_confirmed_final_stats",
  "source": "user_input",
  "is_user_confirmed": true,
  "confidence": "higher_confidence_reference",
  "final_stats": {
    "hp": 183,
    "atk": 150,
    "def": 115,
    "spa": 90,
    "spd": 105,
    "spe": 154
  }
}
```

LLM language:

- May say "user-confirmed final stats."
- Must still not say final battle damage, final turn order, KO, OHKO, or 2HKO unless those explicit systems exist.

### B. `sample_assumed_stats`

Meaning:

- Stats come from a sample file or curated/meta sample.
- The sample represents a plausible set, not the actual opponent unless T1 confirms it.
- It may be useful for rough damage or threat exploration.

Payload semantics:

```json
{
  "status": "sample_assumed",
  "source": "pokemon_stat_samples",
  "sample_id": "garchomp_fast_physical_01",
  "is_user_confirmed": false,
  "confidence": "estimated",
  "final_stats": {
    "hp": 183,
    "atk": 150,
    "def": 115,
    "spa": 90,
    "spd": 105,
    "spe": 154
  },
  "limitations": [
    "Opponent stats are sample-based assumptions, not confirmed."
  ]
}
```

LLM language:

- Should say "assuming the opponent uses the fast physical Garchomp sample."
- Must say the stats may differ from the real opponent.
- Must not say "the opponent definitely has 154 Speed."

### C. `default_assumption_stats`

Meaning:

- The app's existing fallback.
- Current damage estimates compute Level 50, IV 31, EV 0, neutral-nature stats from species base stats.
- This remains the lowest-confidence numeric stat model.

Payload semantics:

```json
{
  "status": "default_assumption",
  "source": "system_default",
  "is_user_confirmed": false,
  "confidence": "rough_reference",
  "final_stats": null
}
```

LLM language:

- Should say "default assumptions."
- Must not imply the opponent is uninvested, neutral, or itemless in the real battle.

### D. `unknown_stats`

Meaning:

- No usable final stat model exists.
- This may be useful in future contexts where a calculation is intentionally withheld instead of falling back.

Payload semantics:

```json
{
  "status": "unknown_stats",
  "source": "unavailable",
  "is_user_confirmed": false,
  "confidence": "unknown",
  "final_stats": null
}
```

LLM language:

- Should ask for or note missing stats.
- Must not infer numeric damage or Speed from unknown stats.

## 4. Proposed Data File Design

Candidate file:

`data/static/pokemon_stat_samples.json`

Recommended top-level shape:

```json
{
  "format": "pokemon_stat_samples",
  "regulation": "pokemon_champions",
  "version": 1,
  "samples": {
    "garchomp": [
      {
        "sample_id": "garchomp_fast_physical_01",
        "label_en": "Fast physical sample",
        "label_ko": "고속 물리형 샘플",
        "source": "manual_sample",
        "confidence": "estimated",
        "format": "pokemon_champions",
        "stats": {
          "hp": 183,
          "atk": 150,
          "def": 115,
          "spa": 90,
          "spd": 105,
          "spe": 154
        },
        "assumptions": {
          "sp_distribution": {
            "hp": 0,
            "atk": 32,
            "def": 0,
            "spa": 0,
            "spd": 0,
            "spe": 32
          },
          "nature": null,
          "item": null
        },
        "notes": [
          "Estimated sample, not user-confirmed.",
          "Do not treat as exact opponent stats."
        ]
      }
    ]
  }
}
```

Recommended validation rules:

- Top-level `format`, `regulation`, `version`, and `samples` are required.
- Species keys use normalized Pokemon ids.
- `sample_id` is globally unique.
- All six `stats` keys are required and positive integers.
- `confidence` starts with `estimated`; later values may include `manual_verified` or `metagame_reference` if source policy is defined.
- `source` should identify whether the sample is manual, imported, or generated.
- `notes` must include that the sample is not user-confirmed.
- No sample should claim exact opponent stats.

Do not create this fixture in v0.34. This is a design-only target for v0.35.

## 5. Payload Design

The cleanest first payload path is to extend `stat_profiles`, because current damage and Speed helpers already use it as the stat source boundary.

Recommended first shape:

```json
{
  "stat_profiles": {
    "opponent_active": {
      "status": "sample_assumed",
      "source": "pokemon_stat_samples",
      "sample_id": "garchomp_fast_physical_01",
      "sample_label_en": "Fast physical sample",
      "sample_label_ko": "고속 물리형 샘플",
      "is_user_confirmed": false,
      "confidence": "estimated",
      "level": 50,
      "final_stats": {
        "hp": 183,
        "atk": 150,
        "def": 115,
        "spa": 90,
        "spd": 105,
        "spe": 154
      },
      "limitations": [
        "Opponent stats are sample-based assumptions, not confirmed.",
        "Do not treat this as the opponent's actual spread."
      ]
    }
  }
}
```

Alternative:

```json
{
  "battle_assumptions": {
    "stat_sources": {
      "opponent_active": {
        "status": "sample_assumed",
        "sample_id": "garchomp_fast_physical_01"
      }
    }
  }
}
```

T3 recommendation:

- Use `stat_profiles.*` as the source of truth.
- Add a top-level `battle_assumptions.stat_sources` later only if multiple systems need a compact audit trail.
- Avoid duplicating stat source in two authoritative locations at first.

Potential `assumption_profile` additions:

```json
{
  "id": "sample_assumed_stats_level50",
  "label": "Sample-assumed stats / Level 50",
  "source": "pokemon_stat_samples",
  "confidence": "estimated_reference",
  "is_user_confirmed": false,
  "stats_used": {
    "attacker": "default_assumption",
    "defender": "sample_assumed"
  },
  "sample_ids": {
    "defender": "garchomp_fast_physical_01"
  }
}
```

## 6. Damage Estimate Behavior

Recommended behavior by source:

- `user_confirmed_final_stats`
  - Use as the highest-confidence stat input.
  - Preserve current `user_confirmed_final_stats_level50` profile semantics.
- `sample_assumed`
  - May be used in a future implementation only when explicitly selected.
  - Must change `damage_estimate.assumption_profile` to a sample-specific profile.
  - Must add limitations such as "Opponent stats are sample-based assumptions, not confirmed."
  - Must keep `is_final_battle_damage: false`.
  - Should support wording like "assuming a fast physical Garchomp sample."
- `default_assumption`
  - Continue existing rough-reference behavior.
  - Do not claim exact battle stats.
- `unknown_stats`
  - Do not calculate from unknown stats unless another explicit fallback is chosen.

Important guardrail:

- Sample stats should not silently flow through `_final_stats_from_profile()` as though they were user-confirmed.
- A future helper should make stat source explicit, such as `_stats_for_role_with_source()` or `_final_stats_from_profile_source()`.
- The damage estimate should surface which side used sample stats.

Suggested future fields:

```json
{
  "derived_stats": {
    "attacker": {
      "attack_stat_used": 150,
      "attack_stat_name": "atk",
      "stat_source": "sample_assumed",
      "sample_id": "garchomp_fast_physical_01"
    },
    "defender": {
      "defense_stat_used": 98,
      "defense_stat_name": "def",
      "stat_source": "user_confirmed_final_stats"
    }
  }
}
```

## 7. Speed Context Behavior

Current policy from v0.28 and v0.30:

- `speed_context` requires both active Pokemon to have user-confirmed final Speed.
- Default Speed fallback is not used.
- Effective Speed includes only supported speed modifiers such as user-confirmed Choice Scarf.
- `is_final_turn_order` remains `false`.

Decision point:

- Should `sample_assumed` stats feed `speed_context`?

Option A - keep `speed_context` user-confirmed only

- Safest.
- Preserves current tests and guardrails.
- Avoids "154 Speed" being read as actual opponent Speed.
- Recommended for the first implementation after this design.

Option B - allow sample stats in `speed_context` with lower confidence

- Useful for rough speed planning.
- Requires explicit `comparison_confidence: "sample_assumed"` and stronger prompt language.
- Still cannot be final turn order.

Option C - add `assumed_speed_context`

- Keeps confirmed Speed comparison separate from sample-based Speed hints.
- More verbose, but safer than mixing sample and confirmed values under the same `speed_context.available: true`.

T3 recommendation:

- v0.35 should keep current user-confirmed-only `speed_context`.
- If a sample is selected, either:
  - keep `speed_context.available: false` with a `sample_hint`, or
  - defer speed use until an `assumed_speed_context` design.
- Do not feed sample stats directly into the existing confirmed speed comparison in the first implementation.

Potential future unavailable shape:

```json
{
  "speed_context": {
    "mode": "choice_scarf_effective_speed_v0.30",
    "available": false,
    "reason": "insufficient_confirmed_final_stats",
    "sample_hint": {
      "opponent_active": {
        "sample_id": "garchomp_fast_physical_01",
        "raw_speed": 154,
        "confidence": "estimated"
      }
    },
    "limitations": [
      "Confirmed Speed comparison requires user-confirmed final Speed for both active Pokemon.",
      "Opponent sample Speed is an assumption, not confirmed.",
      "This does not confirm final turn order."
    ],
    "is_final_turn_order": false
  }
}
```

## 8. UI Direction

### Option A - sample file only, no UI

Pros:

- Safest first implementation.
- Lets schema and repository tests settle.
- No risk of T1 accidentally applying a sample in advice.

Cons:

- User cannot select samples.
- No payload integration yet.

### Option B - Opponent Stat Sample Selector

Pros:

- Lets T1 choose a named sample intentionally.
- Can be attached to the opponent Stats button.
- Can clearly mark `status: "sample_assumed"` instead of `user_confirmed_final_stats`.

Cons:

- Needs UI copy and visual distinction from confirmed final stats.
- Needs reset/override rules with manual final stats.

Suggested UI behavior if implemented later:

- Opponent Stats button opens existing final stat flow plus a "Sample" tab or selector.
- Selecting a sample sets panel stat profile status to `sample_assumed`.
- Manual Save sets `user_confirmed_final_stats` and clears sample metadata.
- Clear returns to `default_assumption`.

### Option C - auto-suggest sample

Pros:

- Low friction.
- Can surface common sets quickly.

Cons:

- Highest overclaiming risk.
- The LLM may treat an auto-suggestion as intentionally selected.
- T1 may not realize the estimate changed.

T3 recommendation:

- v0.34: design only.
- v0.35: repository and sentinel fixture only.
- v0.36 or later: explicit Opponent Stat Sample Selector if T1/T2 approve.
- Avoid auto-application until guardrails are proven.

## 9. Repository / Helper Design

Candidate module:

`core/pokemon_stat_sample_repository.py`

Candidate API:

```python
load_stat_samples(path: Path | None = None) -> dict
list_samples_for_species(species_id: str) -> list[dict]
get_sample(sample_id: str) -> dict | None
validate_sample_schema(data: object) -> None
classify_stat_source(profile: dict) -> str
```

Recommended responsibilities:

- Load `data/static/pokemon_stat_samples.json`.
- Validate top-level fixture structure.
- Validate each sample has all six final stats.
- Normalize species ids.
- Index by species id and sample id.
- Return immutable or copied sample dictionaries.
- Never auto-select a sample.

`classify_stat_source()` should distinguish:

- `user_confirmed_final_stats`
- `sample_assumed`
- `default_assumption`
- `unknown_stats`

This helper should not modify damage or speed behavior in v0.35. It should only make source classification testable.

## 10. LLM Guardrail

Required guardrails:

- Do not describe `sample_assumed` stats as user-confirmed.
- Do not say a sample stat is the opponent's actual stat.
- Damage based on sample stats must be described as sample-assumed.
- Speed based on sample stats must be described as sample-assumed and non-final.
- If opponent stats are default or sample-based, say the real opponent may differ.
- Do not guarantee Speed order from non-user-confirmed stats.
- Do not confirm final turn order unless a future explicit field says it is final.
- Do not infer KO, OHKO, 2HKO, or survival from sample stats alone.
- Do not infer EVs, IVs, nature, item, or ability from a sample unless the sample explicitly provides that metadata and the prompt says it is still assumed.

Good wording:

- "Assuming the opponent uses the fast physical Garchomp sample..."
- "Because the opponent's stats are sample-based, this is not confirmed."
- "Under the selected sample assumption, this rough damage estimate changes..."
- "This does not prove the opponent's actual Speed or final turn order."

Bad wording:

- "The opponent definitely has 154 Speed."
- "You outspeed for sure."
- "This is the opponent's actual spread."
- "This confirms the KO."
- "The sample proves their EVs and nature."
